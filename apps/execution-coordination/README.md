# Execution Coordination v0

This package hosts BC04's engine-independent Run/Attempt state and application coordination plus a local composition adapter. The domain imports only its own types and ports. The Scrapy container adapter is the technical BC05 execution adapter in this fixture-only composition; it invokes the prebuilt Scrapy Collector through Docker CLI and inspects the effective container before start.

The in-memory repository is atomic only inside one process and loses all state if that process exits. There are no retries, durable recovery, distributed leases, BC11 admission, BC06 custody, or productive egress. A successful adapter output stays in private staging until BC04 accepts success; failed, late, canceled, or timed-out outputs are discarded. A container/worker crash is technical status `crashed`, mapped by BC04 to terminal `failed` with diagnostic `WORKER_CRASHED`. Each container receives a private per-Attempt bind mount for output; worker and adapter enforce total byte/record budgets, and the container has a per-file `fsize` limit. There is no aggregate kernel filesystem quota on the host bind mount; bounded concurrency and generated output limits constrain exposure, but this remains a residual limitation.

`adapters.trusted_live_authority.TrustedLiveAuthority` verifies a bounded RFC 8785 snapshot signature against operator-provisioned Ed25519 public keys, checks validity and a configured minimum generation, and installs the authenticated snapshot into BC04's durable authority registry before it can authorize a live run. The registry stores immutable generation history and a monotonic current head per explicit authority ID. Lower generations and same-generation content conflicts fail; exact replays are idempotent. Admission checks the active PostgreSQL head and expiry, so a newer signed snapshot makes the older resolver stale after process restart or authority update. Snapshot installation remains operator-managed; signing keys and trusted public-key rotation are deployment responsibilities, not a BC04 identity service. Key rotation requires distributing the next public key through trusted deployment configuration before installing a snapshot signed by it. Generic `create_run` remains fixture-only. A document's `approved` field alone is never sufficient. Private signing keys are not included in the worker or gateway.

`adapters.execution_capability.ExecutionCapabilitySigner` is the BC04 Ed25519 capability issuer and verifier. `DurableExecutionCoordinator.issue_execution_capability` requires the current running lease and binds the capability to tenant/run/attempt/generation, the immutable live binding, gateway audience, and attempt deadline. Expiry is capped by both lease and execution deadline and cannot exceed two minutes. Lease renewal invalidates the old lease's issue request. BC04's `acquisition_authorization_http` adapter authenticates the gateway and calls a PostgreSQL transaction that locks the run/attempt, compares every live binding and active authority head, then persists one operation admission. Cancellation and operation admission lock the run in the same order: the commit is the linearization point. An admitted request can finish if cancellation follows; in-flight network I/O is not retroactively canceled. The Go gateway's HTTP authorizer is wired to this protocol. The lower-level `make acquisition-live-gateway-container-smoke` uses its explicitly test-only static authorizer; `make authorized-live-json-acquisition` proves the cross-process gateway-to-BC04 PostgreSQL operation path. The fixture-only Docker adapter remains unchanged.

Run local tests with make execution-coordination-tests. make execution-coordination-protected-e2e is a Linux/Docker acceptance target and is required in Integration Security Gate. Direct host execution of Scrapy is not a protected operational path.

The controlled durable live JSON acceptance uses `make authorized-live-json-acquisition`. It requires the existing local PostgreSQL, MongoDB, BC06/RustFS services and their preserved ignored env files. It uses only the controlled Compose TLS source, writes no worker-writable authority or custody credentials, and preserves its named gateway evidence/quota volume. The run creates test-scoped authority and release records; it is not a real-source approval or a production operator workflow.

## Durable coordination review increment

The separate durable adapter persists runs, attempts, leases, finalization reservations, command receipts and BC04 events in the owner schema `execution_coordination`. Fixture execution remains isolated and live admission is a separate application path. The local command `make execution-coordination-reconcile` performs one bounded reconciliation pass over pending reservations. It queries BC05 for the durable publication receipt and, if absent, retries the same stored grant and operation. `--tenant-id` and `--run-id` can scope the pass together; `--limit` is capped at 100 and `--timeout-seconds` at 300. Exit code 0 means all processed rows resolved; 1 means unresolved remote/database failures; 2 means receipt or reservation conflict requiring review. The command never deletes or expires a reservation.

For a run without a finalization reservation, `make execution-coordination-recover-run TENANT_ID=<tenant> RUN_ID=<uuid>` inspects and conditionally applies BC04's normal expiry transition to exactly that run. PostgreSQL time decides lease/deadline expiry under the run-row lock. An expired attempt is marked terminal and its lease token cleared; the run returns to `accepted` if retry budget remains, or becomes `failed`/`timed_out` when exhausted. Repeating the command is safe. It does not renew or reissue an old lease, contact BC05, alter another run, or resolve a run with an active reservation. The command uses the preserved `.env.execution-coordination`; the prerequisite target applies owner migrations. A fresh checkout should initialize isolated local infrastructure through `make execution-coordination-durable-setup`, rather than reuse credentials with a different persistent volume.

Local Make compositions use the explicitly named fixture profile. Production BC05 configuration must contain only the public verification-key ring; BC04 alone holds Ed25519 private signing material. There is not yet a production service-authentication endpoint or BC11 policy integration. A pending reservation intentionally blocks replacement attempts until its publication outcome is resolved.
