## M8.1 operational authoring surface

- PlaybookProposal v2 stores exact declarative candidates per immutable revision with canonical SHA-256. Transcript v4 retains revision history; older proposal and transcript versions retain their existing meaning.
- BC14 `ProposalWorkflow` re-exports the authorized transcript through public interfaces, verifies custody and proposal/source/scope/finding/candidate bindings, applies the current conservative M8 discovery-budget rule, then delegates semantic validation to BC15.
- The protected host composition now wires the BC15 validator by default. `scout_proposal_history`, `scout_validate_proposal`, and `scout_prepare_promotion` expose authorized history, structured diagnostics, and an exact revision/digest handoff. The authoring host has deny-only promotion and registration ports; there is no agent promotion tool.
- The separate `scout-review promote` CLI derives its reviewer principal from the process UID plus a root-owned policy; it accepts no actor, role, tenant, or reviewer identity argument. The mapping rejects root, the configured agent UID, unmapped UIDs, unsafe policy ownership/modes, and reviewers outside the exact SourceRevision allowlist. It takes the session ID, proposal ID, proposal revision, and candidate digest twice. BC14/BC15 are revalidated and all three expected identity values are checked before the immutable M4 registration. Stale proposal revisions and changed candidates are rejected. This is a local OS-account adapter, not production RBAC; no reviewer account or protected policy is provisioned on this host.
- The dependency is one-way from the Scout composition root to the BC15 public validator. BC14 domain/application code does not import BC15. No dependency cycle is introduced.
- Candidate budgets not exceeding discovery budgets is intentionally conservative for the current M8 authoring profile, not a general rule for future acquisitions. Proposals do not grant execution authority; release policy and component limits are rechecked independently.
