# ADR 017 — Scout trusted MCP deployment

- Status: Proposed; HTTP service and bundle tooling are implemented locally, but trusted deployment is not installed or verified.
- Context: PR #9 protects BC15 output in a Docker named volume, but the current local MCP server is launched from the agent-writable checkout and has host access to Docker. Codex CLI 0.170.0 runs configured STDIO MCP servers as local processes; its optional `codex/sandbox-state` capability is experimental and the Scout server does not opt into it.
- Drivers: agent-editable source must not execute in the Docker-capable process; agent-editable project config must not be able to reintroduce privileged STDIO after restart; no runtime build or dynamic import from the checkout; only authorized Scout operations; no public endpoint.
- Alternatives: keep STDIO and require manual trust of project config (rejected: project config and launcher are workspace-editable); install a fixed HTTP service with no managed MCP restriction (rejected: project config could add a privileged STDIO server in a later session); use a pre-provisioned Streamable HTTP service and a Codex managed server identity allowlist (proposed).
- Proposed deployment: a reviewed wheel and a separately built BC15 worker image are installed outside agent-writable paths by an operator. The broker loads only that installed package and fixed protected configuration, accepts no workspace path, and uses the worker image by immutable digest. A prestarted Streamable HTTP server binds only to loopback, authenticates every request, and applies exact Host/Origin/DNS-rebinding checks, payload/session/concurrency/time limits, and existing BC14 source/session authorization. It exposes only the existing typed Scout tools and allowlisted metadata. Docker access belongs to this service identity. Codex is configured with a matching HTTP URL; a forced managed `mcp_servers` identity requirement allows that URL and disables unlisted servers. Project-local configuration remains a convenience layer, never the enforcement layer.
- Platform identity: the protected broker deployment target is a separately administered Linux VM or host. The broker uses a dedicated service UID with access to the Linux Docker daemon; the authoring user has no shell, Docker socket, VM administration, reviewer credential, or policy-write access there. On the current macOS development host, Docker Desktop is shared with the interactive developer/Codex identity and is not an acceptable broker boundary: a container with that socket can exercise daemon-level authority available to the host user. Native macOS is also unsupported because the current trusted composition relies on Linux UID/process and worker isolation semantics. macOS is a client only, reaching the Linux broker through an operator-managed loopback SSH forward and the managed MCP identity allowlist. The SSH tunnel key is held by a separate root-managed `scout-tunnel` account and cannot be read by Codex. A same-UID mode bit or container boundary is not the isolation proof.
- Build and updates: the repository now has Streamable HTTP service and bundle tooling. Bundle tooling pins Python artifacts from the lockfile, requires a digest-pinned Python base for the BC15 image, records the resulting image ID and file hashes, and stages the package without administrative privileges. The manifest is not signed, the source tree is dirty, and the package has not been built from a reviewed release commit or installed by an operator. The running service does not build an image or import from a checkout.
- Consequences: no broker tools are available until an operator installs the service and managed requirements. The project config points to optional loopback HTTP so ordinary Codex sessions remain usable when the broker or token is absent; protected Scout operations still require the separately provisioned broker and managed identity, and the checkout STDIO launcher exits without starting Python. The HTTP path has deterministic development tests, but no protected service identity, active managed Codex allowlist, or provisioned deployment has been proved. Deterministic tests do not prove the deployment boundary.
- Risks: loopback is reachable by other local processes, so bearer/OAuth credentials must not reach model-generated shell commands; Codex network and environment filtering must be tested under the enforced managed policy. Docker daemon compromise, host administrator, kernel/container escape, and local operator replacement remain out of scope.
- Validation before acceptance: test the actual effective managed requirements on macOS and Linux; prove workspace edits cannot start unapproved STDIO before and after Codex restart; prove package/config/dependency/image files resist writes; prove the service alone can use Docker and Codex cannot; test unauthenticated/revoked/cross-session requests, Host/Origin/rebinding, schemas, body/time/concurrency bounds, replay/acceptance, private-volume integrity, restart/reconciliation, cleanup, and fixed image digest. ADR 017 remains Proposed until human review.
