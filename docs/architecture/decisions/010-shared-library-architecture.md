# ADR 010 — Organização e promoção de bibliotecas compartilhadas

- Status: Proposed.
- Contexto: o monorepo prevê aplicações em múltiplas linguagens, mas hoje só tem o módulo interno BC14 em Python, contratos draft, tooling e infraestrutura de teste. Não há `libs/`, `packages/`, ou workspaces Go/Rust/TypeScript.
- Problema: dar um destino estável a código realmente reutilizável sem publicar agregados internos, criar workspaces vazios, acoplar bounded contexts ou transformar cada adapter em biblioteca.
- Drivers: ownership DDD, Clean Architecture, import paths estáveis, release independente apenas quando útil, dependências controladas, teste de consumidores, custo mínimo de manutenção e continuidade dos gates S1.
- Decisão proposta: adotar `libs/<language>/<library>/` como destino canônico para novas bibliotecas compartilhadas. `libs/` só nasce com library real, dono e consumidor. Bounded contexts permanecem módulos internos aos deployables que os hospedam; adapters permanecem junto do contexto até que uma interface estável e segundo consumidor justifiquem promoção. Contratos versionados seguem em `contracts/<context>/<version>/` e não carregam regras internas.
- Termos: technical library é capacidade coesa reutilizada; SDK é cliente de API/contrato público; framework adapter implementa porta do proprietário; plugin implementa extensão pública e passa conformidade; contract package contém esquema/wire types; deployable é unidade de build/release/operação. Nenhum desses conceitos equivale a bounded context.
- Decisão por linguagem: Go usa packages em módulos com caminhos VCS estáveis; criar `go.work` apenas quando múltiplos módulos reais precisarem de desenvolvimento conjunto e testar também sem workspace. Python usa distribution em `libs/python/<distribution>/` com `src/<import_name>/`; adicionar ao uv workspace apenas com consumidor real e separar dependências runtime. Rust cria crates e Cargo workspace somente com crates reais. TypeScript cria pacote com exports públicos explícitos e pnpm workspace somente com consumidores existentes. Não criar projetos vazios.
- Taxonomia lógica: Foundation, Observability, Persistence, Networking, Security, Capture, Testing e Developer Tooling são categorias de catálogo, não níveis de diretório. Cada library futura terá `library.yaml` pequeno, owner, responsabilidade/exclusões, visibilidade, estabilidade, consumidores, dependências, versão/API, testes e depreciação. O manifesto só será validado por tooling quando houver consumer executável da máquina.
- Critério de promoção: responsabilidade coesa, interface identificável, consumidores nomeados/necessidade comprovável, benefício sobre código local ou terceiro, owner, política de dependências/licença, testes isolados e política de release/depreciação. Não criar buckets genéricos `common`, `utils`, `helpers` ou `shared-core`.
- Alternativas: manter `packages/` como diretório universal; diretórios por categoria; promover `mozaic-observability` e `mozaic-postgres` agora. Diretório universal omite limites de toolchain; categoria como caminho acopla release à taxonomia; `mozaic-postgres` não tem consumidores/API compartilhada demonstrados. Como implementação experimental desta proposta, S1.5 cria somente `mozaic-observability`: API stdlib estreita, consumida pela aplicação Scout, com testes independentes e sem dependências runtime. A estabilidade pública e o escopo definitivo aguardam revisão humana.
- Consequências: `apps/scout/scout/adapters/postgres/repository.py`, migration SQL, receipts/outbox e regras CAS continuam de BC14; psycopg e jsonschema permanecem dependências diretas. `mozaic-observability` contém apenas eventos estruturados allowlisted e correlation context; não configura logging global e não importa Scout. O uv workspace instala apenas Scout e esta library; o pacote tem testes independentes e documentação/manifeste experimental.
- Migração: não existe `packages/` para renomear. Manter caminhos/imports/contratos já presentes. Se surgir `packages/`, inventariar API/consumidores e manter aliases ou compatibilidade durante migração; mudanças de Go module path, Python import ou package exports exigem plano versionado, sem rename em massa.
- S1.3: G1 replay de aplicação após restart com reautorização agora tem um teste de processo/PostgreSQL; G2 reconciliação BC06/órfãos e G3 lease/reclaim/backoff da outbox permanecem incompletos e são gates de S1. Nenhuma library pode modificar semântica de comandos, transactions, receipts, estado ou ownership. Esta ADR não fecha S1.
- Riscos e pendências: a política é proposta e não testada em linguagens sem código; critérios de publicação, namespaces/organizational owners e retenção/depreciação públicos requerem revisão humana. Nenhuma decisão fica Accepted automaticamente.
- Critérios de validação: primeiro library consumer real; validar build/install por linguagem, imports unidirecionais, testes de consumidor, política de compatibilidade e ausência de acoplamento a domínio privado; revisão humana de ownership e security.
