# ADR 016 — Scout Authorized HTTP no host MCP

- Status: Proposed; implementação local experimental.
- Contexto: PR #7 integrou o host MCP STDIO a fluxo offline com fixtures. BC14 já possui adapter HTTP experimental, política local, budget PostgreSQL e topologia opcional de egress Squid. O host ainda não conectava essas capacidades.
- Problema: permitir um fetch incremental de URL sem transformar URL em autorização, duplicar o adapter HTTP, ou expor bytes brutos ao transcript/modelo.
- Drivers: ownership BC14/BC06/BC11/BC15; source revision fixa; GET/HTTPS; autorização por origem/path e hop; budget durável; recibo verificável de bytes; schema MCP fechado; compatibilidade BC14/BC15 preservada.
- Alternativas: implementar nova pilha HTTP no MCP host; delegar fetch ao shell do Codex; usar o `HTTPDiscoveryTool` existente através do proxy de egress e compor a persistência de captura pela aplicação BC14.
- Trade-offs: reuso do adapter reduz duplicação e centraliza normalização, redirect e limite de bytes. O host continua STDIO local e a configuração de identidade/policy/custody é somente de desenvolvimento. O proxy Squid protege o caminho implementado de fetch, mas não contém o processo Codex nem sua shell separada.
- Decisão proposta: `scout_fetch` recebe apenas `session_id`, `expected_version` e URL. BC14 carrega source/revision da sessão, valida URL contra source e scope, inicia command receipt, invoca `HTTPDiscoveryTool` com contexto do host e ledger PostgreSQL, grava os bytes finais no adapter local de custody, verifica digest/identidade e sela observation/manifest. Redirects passam por reautorização e budget em cada hop. Links em escopo são retornados como dados para decisão; nenhuma navegação acontece sem nova chamada sensível.
- Ownership: BC14 possui a operação HTTP incremental, observation, manifest, finding, proposal e command receipt. O host MCP é adapter. BC06 continua dono da custody; o filesystem local é double. BC11 continua dono da autorização; arquivo local é double. BC01 resolve source no composition local. BC15 continua proprietário do draft/validate/replay e consome transcript público versionado.
- Consequências: nenhuma alteração aos schemas Scout v1 ou CapturePlaybook draft v1. A resposta final mantém bytes originais fora do retorno MCP/transcript, retornando apenas texto extraído limitado, links autorizados e refs/digests. Os corpos intermediários de redirect ainda não são anexados ao manifest. `scout_links` não é ferramenta separada nesta fase: `scout_fetch` retorna links candidatos.
- Riscos: process isolation do Codex não está implementado; shell/rede fora da ferramenta não é bloqueada. Integrações BC01/06/11 são doubles locais. URL semantics, DNS e ACL dependem de proxy e runtime; ausência do broker encerra o fetch. O arquivo de approval local não é autenticado criptograficamente.
- Critérios de validação: schema fechado e host identity; URL segment/encoding; redirects para destinos privados ou fora do scope; DNS/IP IPv4/IPv6, CNAME e rebinding no broker; limites/timeout/compressão; budgets persistentes sob concorrência/cancelamento/restart; custody digest; network deny; prompt injection como dado; smoke controlado HTTPS pelo MCP, sem bypass, CAPTCHA ou login; operação offline e replay BC15.
