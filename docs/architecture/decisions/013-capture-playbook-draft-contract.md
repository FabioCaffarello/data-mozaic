# ADR 013 — CapturePlaybook draft artifact

- Status: Proposed
- Contexto: BC14 emite `PlaybookProposal`; BC15 é dono de revisões de playbook, validação e release. Scout v1 não é o contrato de configuração do runtime.
- Problema: produzir um candidato revisável e reproduzível sem promover uma proposta Scout, gerar código, ampliar autorização ou introduzir um runtime de captura.
- Drivers: ownership BC15; vínculo a proposal/finding/evidence; subset DSL fechado; replay somente por bytes capturados; status de draft separado de aprovação e release; compatibilidade futura sem alterar Scout v1.
- Alternativas: armazenar YAML livre em BC14; ampliar `PlaybookProposal`; criar um serviço BC15 agora; manter candidate separado e validar localmente em pacote proprietário de BC15.
- Decisão proposta: `CapturePlaybookDraft` é um artefato candidato versionado e propriedade de BC15, referenciando `proposal_ref`, `finding_id` e evidências. O draft v1 permite somente HTTP GET, descoberta de links same-origin/path, paginação limitada e saída raw, com budgets aprovados explícitos. Não possui selectors, código embutido, credenciais ou ações arbitrárias. Parser YAML usa safe loader com chaves duplicadas rejeitadas; schema, semântica, capability e escopo são validados antes do replay.
- Replay: carrega somente fixtures capturadas com digest verificado. Nenhum client de rede é importado pelo pacote; URL sem fixture, erro de digest, byte/budget excessivo ou resposta inválida gera falha visível. Um replay aprovado não prova comportamento em produção.
- Consequências: contrato `capture-playbook-draft/v1` é illustrative e não é contrato de runtime homologado. BC15 não se torna serviço e o draft não é `PlaybookRevision` aprovada, build ou `BotRelease`. A integração Codex exige tool host, autorização executável, isolamento e adapters produtivos de evidência/trace antes de exploração real.
- Riscos / gates: transcript/approval receipt local não é autenticação criptográfica; host deve autenticar aprovação e identidade. O DSL não autoriza requests por si só. Sem sandbox e egress enforcement, o workflow não pode ser exposto a agente externo.
- Validação proposta: schema e semântica negativas, referência cruzada de evidências, URL scope, duplicate YAML keys, integridade fixture, falha visível por fixture ausente, golden E2E multipágina sem rede.

## Gate de filesystem — revisão PR #9 (Proposed; implementação condicionada)

- Cenário suportado pelos primitives atuais: raiz privada administrada pelo executor, em que outros principals não têm permissão de renomear seus componentes. `O_NOFOLLOW`, `dir_fd`, `fstat`, hard links e `flock` protegem contra symlinks iniciais e substituições feitas por processos sem acesso de escrita à raiz.
- Limite demonstrado: depois de aberto, um diretório pode ser renomeado por outro processo com as permissões necessárias. O descritor continua referindo-se ao mesmo inode e operações relativas a ele podem publicar bytes em sua nova localização. Verificar a identidade depois só detecta o movimento após a escrita.
- A composição Codex atual não satisfaz a premissa de raiz exclusiva: Codex tem `workspace-write` sobre o artifact root; BC15 é executado por comandos dessa mesma sessão e sob o mesmo UID. `0700` não separa processos com o mesmo UID e `flock` é cooperativo.
- Alternativa A (ownership exclusivo): suficiente contra UIDs diferentes quando o executor e seus ancestrais são administrados por um principal confiável; `0700` sob o UID da sessão Codex não separa processos desse mesmo UID. Criar e manter UID dedicado exige instalação privilegiada, provisioning e tratamento diferente no macOS e CI, portanto não é a menor composição local.
- Alternativa B (executor isolado): proposta para este fechamento. O host MCP confiável, iniciado antes de o modelo receber ferramentas, oferece operações BC15 tipadas; ele recebe bytes de fixture reautorizados por BC14/BC06, draft e referências de sessão, e inicia um executor efêmero. O resultado raw vive em volume nomeado do daemon, sem bind mount do workspace, e o agente recebe somente relatório/manifesto permitido. O container não recebe socket Docker, rede, capabilities ou rootfs gravável. O MCP não oferece API Docker genérica nem caminhos do executor.
- Alternativa C (sandbox filesystem): a sandbox Codex atual nega ao processo de shell o socket Docker local em `$HOME/.docker/run/docker.sock` (teste `codex exec --sandbox workspace-write`: `PermissionError`). Ela não concede a BC15 escrita diferenciada no workspace e, isoladamente, não substitui o executor. O MCP stdio é uma ferramenta confiável separada do shell e precisa manter sua interface restrita. Docker Desktop executa o daemon numa VM Linux; volumes nomeados ficam no armazenamento gerido pelo daemon, enquanto bind mounts passam caminhos nativos do host à VM. Linux/GitHub Actions usa containers no kernel do host; isso não é uma VM e não protege contra escape/kernel comprometido.
- Decisão proposta, ainda não Accepted: usar B como proprietário operacional da publicação, com o Codex sem acesso ao daemon/socket e sem acesso aos mounts/volume; o MCP valida identidade/sessão contra BC14 e passa fixtures verificadas em canal limitado. A confiança não depende só do socket: esquema fechado, operação específica, autorização da sessão, limites de tamanho/tempo/concorrência, imagem fixada para a execução e retorno allowlisted são parte do contrato. O container recebe apenas o volume de saída e inputs limitados; não recebe fixture path, output path ou comando controlado pelo modelo.
- Custos: imagem do executor precisa estar pronta antes da sessão MCP/modelo; chamadas passam serialização e criação de container; volume e metadados de execução precisam de retenção/cleanup; Docker Desktop e daemon local são pré-requisitos. Linux CI testa o mesmo executor sem alegar isolamento contra kernel do runner. Instalações sem runtime verificado falham fechadas. O teste de integração deve comprovar que o sandbox Codex não abre o socket, o broker não aceita path/comando arbitrário, e um processo adversarial com permissões efetivas do agente não move o volume/diretório privado nem causa bytes externos.
- Gate antes de qualquer alegação de segurança: provar imagem e volume privados na composição real, exercício de bypass pelo Codex workspace-write, rename adversarial pela API protegida, nenhuma escrita externa, replay+acceptance pelas duas fixtures e testes Linux CI. A reprodução direta same-UID permanece válida como limite do writer local; ela não pode ser renomeada como teste protegido. Se a composição real falhar ou não puder ser exercitada em macOS e Linux, o resultado permanece **NO-GO**. Esta proposta não promove ADR a Accepted e aguarda decisão humana.

## Implementação local — evolução interna do transcript

O transcript BC14→BC15 evoluiu para `scout-transcript-draft/v2`, sem alteração do Scout v1 nem da DSL CapturePlaybook draft/v1. O motivo é que v1 não carrega URL de entrada, URL efetiva após redirect ou sequência/relação de observações; BC15 não pode reconstruí-las por ID ou timestamp. BC14 persiste esses fatos no agregado e exporta-os por sequência explícita. BC15 mantém leitura estrutural de v1 para diagnóstico, mas recusa gerar um playbook a partir de v1 por falta de identidade inicial inequívoca. Consumidores devem negociar explicitamente a versão do transcript. O formato v2 continua draft/illustrative.

Replay Execution e Acquisition Acceptance são gates separados. Replay materializa `output.raw` como bytes e verifica operações, budgets e integridade. Acceptance usa expectativas mantidas fora do transcript e do draft para verificar início, cobertura exigida, relação de navegação, identidade/digest dos outputs e limites. Isso não extrai nem afirma records estruturados. Não se introduziu DSL v2.

Compatibilidade: dados persistidos antigos de sessão ainda hidratam com metadados opcionais ausentes; novas sessões HTTP persistem sequência. Uma sessão HTTP antiga sem sequência pode exportar metadata, mas não pode produzir draft confiável. Novos consumidores devem rejeitar v1 para autoria ou manter um adapter explicitamente versionado que obtenha uma origem inequívoca fora da ordenação das páginas.
