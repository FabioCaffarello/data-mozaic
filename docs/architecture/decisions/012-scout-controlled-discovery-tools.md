# ADR 012 — Ferramentas controladas de descoberta do Scout

- Status: Proposed
- Contexto: S1 é um fluxo offline. O próximo consumidor planejado é um host de ferramentas para exploração HTTP explicitamente autorizada; não existe adapter produtivo de BC01, BC06 ou BC11.
- Problema: evitar que prompts, URLs livres ou uma biblioteca cliente possam ampliar origem, caminhos, requests, duração, dados preservados ou credenciais.
- Drivers: cada request e redirect deve ser revalidado; identidade/autorização não vêm dos argumentos do agente; DNS precisa ser validado no ponto de conexão; bytes e trace têm owners distintos; execução deve ser isolável do agente que consome as ferramentas.
- Alternativas: aceitar URLs e escopos do prompt; usar client HTTP com redirecionamento automático; delegar enforcement a um proxy corporativo; client HTTP sem redirects automáticos através de um proxy de egress explícito com ACL de destino.
- Decisão proposta: ferramentas recebem contexto autenticado do host e consultam registro local de fontes e aprovação por principal/revisão. Cada autorização liga origens a seus próprios prefixes, métodos GET e budgets; a interseção é por origem, sem produto cartesiano. O adapter normaliza HTTPS e paths, rejeita userinfo, portas não padrão, fragmentos, traversal e separators codificados. Redirects são manuais, reautorizados e consomem budget. `AiohttpSquidTransport` exige o proxy de egress interno; Squid resolve os hosts destino, permite apenas CONNECT 443 para hostnames registrados e bloqueia ranges privados/especiais. O adapter não envia credenciais/cookies e limita bytes e tempo. Respostas raw e traces são enviados por portas BC06/BC14, sem acesso direto às respectivas tabelas.
- Consequências: o primeiro runtime usa HTTP/TLS e não faz browser, login, POST ou execução de conteúdo. O arquivo de política local é um input administrativo de desenvolvimento, não contrato público nem substituto futuro de BC01/BC11. O budget ledger PostgreSQL persiste o scope inicial e não permite widening durante a sessão. A topologia Docker opcional mantém o worker em rede interna e Squid como único serviço com egress; ainda não há MCP/tool host nem contenção de shell/rede do agente externo.
- Limites: policy no adapter e allowlist do proxy impedem bypass dentro do caminho implementado, mas não limitam um processo externo de agente que ainda possua shell ou rede. CONNECT TLS não expõe path/method ao Squid; o adapter os aplica. Integração Codex só pode afirmar contenção quando o host efetivamente restringir esses canais. ACL de endereços especiais não substitui egress firewall no deployment.
- Riscos: diferenças de normalização entre client e origin server, DNS resolver mal configurado, expiração durante request, dados sensíveis em conteúdo, redirecionamentos e policy local desatualizada.
- Critérios de validação: scheme/host/port/IDNA, escapes e segment boundaries; associações cruzadas de origin/path; redirect cross-origin; DNS com respostas públicas e especiais; limite de requests/duração/bytes; respostas com cookies/compressão; transporte injetado hermético; teste do runtime real para provar isolamento de processo e egress antes de uso por agente.
