# ADR 018 — Collector Playbook v2, Typed IR, and Python HTTP Reference

- Status: Proposed
- Contexto: BC15 draft/v1 creates acquisition drafts and replays raw fixture pages; it has no structured extraction or compiler. PR #10 needs one executable vertical slice without transferring extraction semantics to BC14 or introducing framework coupling.
- Problema: define a versioned declarative contract and stable intermediate representation that can be compiled to an offline reference bot while preserving draft/v1 consumers and failing clearly for unsupported engine capabilities.
- Drivers de decisão: keep v1 unchanged; closed YAML/JSON Schema contract; explicit evidence, scope, budgets, types, bindings, and failure policy; no code execution in playbooks; deterministic builds; no live HTTP capability in this backend; acceptance from independent fixtures.
- Alternativas: extend v1 in place (rejected because it changes old semantics); compile directly from YAML (rejected because backend/tooling would duplicate semantic validation); use an unbounded general graph interpreter (rejected because it adds control-flow surface without consumers); implement a browser engine now (rejected because deployment and isolation gates remain open).
- Trade-offs: a bounded Typed IR and generated operation-specific Python add codegen and manifest maintenance, but separate BC15 meaning from runtime helpers. `selectolax` adds a native dependency, offset by the CSS/HTML5 selector support and verified macOS arm64/Linux x86_64 wheels for Python 3.12. Decimal output is a canonical base-10 JSON string to avoid binary float ambiguity.
- Decisão proposta: preserve `capture-playbook-draft/v1`; add draft-only `capture-playbook-draft/v2` and `collector-ir/v1`; represent dependencies as a typed DAG with only a finite `pagination.bounded/v1` operator; add the versioned Python HTTP Reference capability profile; generate Python specific to IR operations and run it only against digest-verified fixtures. Capability mismatch must fail before build directory publication.
- Consequências: BC15 owns parser semantics, validation, IR, capability checking, compiler, local BotBuild and verification. BC14 continues to own observations/findings/proposal/evidence references; BC06 remains raw artifact custodian; BC11 remains authorization owner. The backend performs no source network requests and does not approve production execution or release.
- Riscos: selector match counts do not prove business correctness; profile/manifest digests are not signatures; macOS `sandbox-exec` denies network and CPU/time, but does not establish a memory limit equivalent to Docker; Linux CI must run generated bots in a non-root `--network none` container with resource caps. The Scout trusted deployment remains independently gated by ADR 017.
- Critérios de validação: draft/v1 regression tests; v2 schema and semantic negative tests; IR golden digest; deterministic distinct generated sources; HTML/JSON/pagination examples compared with independent expected records; browser capability negative; build verifier tamper/path tests; macOS effective network-denial probe; Linux CI execution in `--network none`; all ADR statuses remain Proposed until human approval.
